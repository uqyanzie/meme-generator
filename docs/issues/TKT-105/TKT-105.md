# TKT-105: Duplicate Checkout / Double Billing Creation

- **Execution Order:** 5
- **Layer:** Frontend + Backend
- **Status:** Open
- **Related Tickets:** [TKT-106](../TKT-106/TKT-106.md)

---

## Summary

Clicking the "Subscribe" (Berlangganan) button multiple times under slow network conditions creates duplicate pending checkout records for the same package.

## Reported Behavior

A user experiencing slow internet clicked "Subscribe" twice, resulting in two pending checkouts for the identical package.

## Expected Behavior

Checkout creation must be idempotent and guarded against duplicate submissions: rapid or repeated clicks for the same purchase intent reuse the same `Idempotency-Key`, disable in-flight submission in the UI, and return the existing checkout cleanly without creating duplicate pending records.

## Potential Impact

Risk of double billing and cluttered/inconsistent pending payment records.

---

## Initial Codebase Touchpoints

- `web/src/lib/queries.ts` (`useCheckout` generates a brand new `crypto.randomUUID()` for `Idempotency-Key` on every `mutationFn` call).
- `web/src/app/pricing/page.tsx` ("Berlangganan" button is not disabled while `checkout.isPending`).
- `api/internal/modules/subscription/service.go` & `repository.go` (`Checkout` checks `CheckoutByIdempotencyKey` before `CreateSubscription`, but concurrent requests with the same `Idempotency-Key` can hit the unique index `payments_idempotency_key_idx` and fail with 500 instead of replaying).

## Pending Decisions (Discuss Before Implementation)

- [x] **Cross-refresh pending checkout deduplication:** **Yes** — in addition to fixing client `Idempotency-Key` lifecycle + UI pending disable + backend `payments_idempotency_key_idx` unique-violation replay, the backend will also reuse an existing pending checkout for the same `(user_id, plan_id)` even if the user refreshes the page or opens another tab and submits a new `Idempotency-Key`.
